# 複数Issue 並列開発計画ドキュメント生成

引数で指定した複数の GitHub Issue について、デグレ・手戻りを最小化しつつ並列開発が可能な計画と、各 Issue の作業注意点ドキュメントを `doc/plan-<開始>-<終了>/` 配下にまとめて生成する。

サマリーは経過記録として更新する想定で、進捗ステータス表を空欄で初期化する。

## 入力（$ARGUMENTS）

以下のいずれかの形式を許容する:

- 範囲: `146-154`
- カンマ区切り: `146,147,154`
- スペース区切り: `146 147 154`
- 単一: `150`

引数が空の場合は中断し、フォーマット例を提示する。

## Step 1: 引数解析と前提検証

1. `$ARGUMENTS` をパースして対象 Issue 番号集合 `ISSUES` を確定する
2. `MIN = min(ISSUES)`, `MAX = max(ISSUES)` を求めて出力フォルダ名を `doc/plan-<MIN>-<MAX>/` に決定
3. `test -d doc/plan-<MIN>-<MAX>` で既存フォルダの有無を確認
   - 既存ならユーザーに上書き / 中断 / 別名 のいずれかを確認
4. `git rev-parse --abbrev-ref HEAD` で現ブランチを確認し、`main` の場合はユーザーに「ドキュメント用ブランチを切るか」を確認

## Step 2: Issue 情報取得

各 Issue について並列で `gh issue view <番号> --json number,title,labels,state,body` を取得し、以下を抽出する:

- タイトル
- 本文（概要 / 実現したいこと / 受け入れ基準 / 難易度）
- ラベル（enhancement / bug 等）
- ステート（OPEN / CLOSED）

`CLOSED` の Issue が含まれる場合はユーザーに確認する。

## Step 3: コードベース調査（影響範囲の見積もり）

各 Issue の内容から、触られそうなレイヤを軽く調査する。並列度を最大化するため `Glob` / `Grep` を活用：

- **DB**: `db/schema.hcl` を読んで既存テーブルとの関係（新規 / 既存拡張）を判断
- **Server**:
  - `packages/server/src/routes/` 配下に既存 API があるか
  - `packages/server/src/services/` 配下に既存 Service があるか
  - 認証・認可・送信パスへ踏み込むか（`middleware/auth.ts` / `socket/messageHandler.ts` 等）
- **Client**:
  - `packages/client/src/components/` / `packages/client/src/pages/` で関連コンポーネントを特定
  - 競合危険ファイル（例: `UserAvatar` 系 / `MessageInput` / `ChatPage.tsx` / `MessageActions.tsx` / `ChannelList.tsx` / `AppLayout.tsx`）に触る Issue を洗い出す

調査は深堀りしない。**ファイル衝突の有無を判定するための一次見積もり**にとどめる。

## Step 4: フェーズ分割と並列グループ決定

以下の方針で Phase 1 〜 N に分ける:

1. **競合危険ファイルを同フェーズで複数 Issue が触らない**ように分離する
2. **後続 UI が乗る基盤系**（プレゼンス / ヘッダー縮小 等）は早いフェーズに置く
3. **横断的に既存コードへ手を入れる Issue**（送信パスへのフック / 認証ミドルウェア改変 等）は最終フェーズに置く
4. 同一フェーズ内では「新規ファイル中心」「触るファイルが完全分離」となる Issue を並列グループにする

依存関係の根拠（なぜこの順）は summary.md に文章で記録する。

## Step 5: ドキュメント生成

`mkdir -p doc/plan-<MIN>-<MAX>/` のあと、以下を `Write` で生成する。

### 5-1. `summary.md`（1ファイル）

経過記録運用を前提に、以下のセクションを必ず含める:

- 全体方針（デグレ抑制 / 手戻り抑制 / 並列性確保 の3軸での説明）
- 想定マージ順 / 並列グループ表（Phase / Issue番号 / 難易度 / 並列可否 / 触るレイヤ）
- Phase 並列グループの根拠（なぜそのグループ化か）
- 依存関係（テキスト + ASCII 図）
- **進捗ステータス表**（Issue / 計画ドキュメント / ブランチ / PR / AI テスト設計レビュー / Playwright / マージ / 備考 — 空欄で初期化）
- 共通注意事項（AGENTS.md の TDD フロー遵守 / `db/schema.hcl` 経由の DB 変更 / PR テンプレ全埋め / 競合危険ファイル列挙）
- 仕様確認事項（実装着手前にユーザーへ確認すべき論点を列挙し、対応する `issue-XXX.md` への参照を付ける）

最終更新日は `date +%Y-%m-%d` の出力をそのまま記載する。

### 5-2. `issue-<番号>.md`（Issue ごとに1ファイル）

各 Issue について以下のセクションを必ず含める:

- 見出しに `# Issue #<番号> — <タイトル>` と `> Phase X / 並列OK or 制約 / 難易度: 低/中/高` のサマリ行
- **概要**（Issue 本文の要約 — 箇条書き）
- **仕様確認事項**（曖昧な点を箇条書き、推奨デフォルトを併記）
- **影響範囲**
  - DB（`db/schema.hcl` への変更案）
  - Server（新規 / 修正対象のファイル列挙）
  - Client（新規 / 修正対象のファイル列挙）
  - Socket イベント設計（必要な場合）
- **並列実行時の競合警戒**（同フェーズ内 / 他フェーズで触るファイルの重なり）
- **実装ポイント / 落とし穴**（具体的な技術的注意点）
- **テスト観点**（ユニット / 統合 / フロントエンドの観点で箇条書き）
- **ステータス（経過記録）**（計画作成日 / ブランチ / PR / マージ / 備考 — 空欄で初期化）

仕様確認事項は **MVPでの推奨デフォルトを必ず併記**する（ユーザーが判断しやすくするため）。

### 5-3. クロスリンク

- `summary.md` の進捗ステータス表から各 `issue-XXX.md` へリンクを張る
- 各 `issue-XXX.md` には summary.md への戻りリンクは不要（フォルダ内で完結）

## Step 6: 結果報告

生成完了後、以下を1つのメッセージで提示する:

```
## 計画ドキュメント生成完了

- 出力先: doc/plan-<MIN>-<MAX>/
- ファイル数: <件数>（summary.md + issue-XXX.md × N）
- フェーズ分割: Phase 1 [#X #Y #Z] / Phase 2 [...] / ...
- 並列着手可能なグループ: ...
- 仕様確認事項: <件数> 件（着手前に確認推奨）

最初に着手する候補: <Phase 1 の中で最も独立性が高い Issue>
```

## 制約事項

- **コードへの変更は行わない**（このコマンドは計画ドキュメントの生成のみ）
- **既存の `doc/` 配下にあるドキュメントは触らない**
- **Issue 本文に書かれていない仕様を断定しない**（曖昧な点は「仕様確認事項」に列挙する）
- **絵文字は使わない**（プロジェクトのドキュメント慣習に合わせる）
- **DB 変更案を提示する場合は `db/schema.hcl` の既存定義を読んで整合性を確認する**（既存テーブルとの関係を曖昧に書かない）
