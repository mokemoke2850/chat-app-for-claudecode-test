# Feature Dev

1. `AGENTS.md`、`doc/ai-review-tdd-guide.md`、Issue と関連仕様を読む。
2. ブランチを作り、テスト観点を整理してテストファイルへ `it.todo` のスケルトンを書く。
3. 作成担当と別コンテキストの reviewer agent を起動する。Issue、関連仕様、既存実装・テスト、差分を渡し、共通レビュー観点による判定を求める。
4. `CHANGES_REQUESTED` なら修正し、同じ reviewer に再レビューを依頼する。`APPROVED` までアサーションを書かない。
5. 承認済みスケルトンをアサーション付きテストへ変換する。プログラム実装前に対象テストを実行し、期待動作の未実装を原因として失敗することを確認して RED のコマンドと代表的な失敗を記録する。構文エラー、モック不足、環境障害は RED とみなさない。
6. テストが定義する仕様に合わせてプログラムを実装し、同じ対象テストを再実行して GREEN を確認する。既存実装がすでにテストを満たす場合は、重複実装せず証拠と理由を記録する。
7. 対象テスト、`npm run build`、`npm run test`、未実装テスト残存確認を行う。
8. `AGENTS.md` が定める高リスク変更では、同じ reviewer に実装差分とテストのレビューを依頼し、`APPROVED` まで修正する。
9. 画面影響がある場合は `$codex-browser-dev` を使い、レビューで定めたシナリオ、コンソール、ネットワークを確認する。画面影響がなければ `N/A` の根拠を記録する。
10. `.github/PULL_REQUEST_TEMPLATE.md` を埋め、RED/GREEN、レビュー、検証の結果を含む PR を作る。マージはしない。

既存の goal 実行中は通常の AI レビューを理由に停止せず、仕様資料から決められないプロダクト判断だけをユーザーへ確認する。重大な技術指摘は修正し、PR と完了報告へ記録する。
